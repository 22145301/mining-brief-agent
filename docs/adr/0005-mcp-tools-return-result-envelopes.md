# MCP 工具统一返回结果信封：缺失与故障都是字段，不是异常

三个 server 的每个工具都返回一个**顶层对象信封**（`NewsSearchResult` / `ArticleLookup` / `PriceLookup` / `PriceSeries` / `ResourceExtract`），把"取到了 / 真的没有数据 / 取数降级"做成**正常返回的字段**（`status` / `source_status` / `reason`）；只有参数非法这类"工具自己坏了"才抛异常。

信封与领域类型集中定义在一个**共享类型包**里，三个 server 与 agent 共用同一份，避免三份近似类型各自漂移。题面只钉了工具名与参数，没有规定返回类型（原文即 `search(query, days)` · `fetch_article(url)` 这样的两行），所以返回形状是我们的设计空间。

## Considered Options

- **裸返回 + 异常表达失败**：最符合常规直觉。否决，两点。其一，返回裸列表时 SDK 会隐式包成 `{"result": [...]}` 并把它发布进 `output_schema` —— 即"裸返回"并不真的裸，是**别人替你包**，包成什么样不归你管；`tools/list` 里出现不是我们领域语言的包装层，会削弱"工具契约是产品的一部分、独立可测"这一主张，被问"你的 outputSchema 长什么样"时也不该答"SDK 替我包的"。其二，"今天确实没有这条新闻"（事实）与"mining.com 挂了"（故障）会被挤进同一个异常通道，而简报第 6 节存在的全部意义就是如实区分二者，A7 也依赖这个区分。
- **折中（只有可能缺失的工具用信封）**：契约形状不统一，"哪些工具有信封"要靠记，调用方要维护两套剥法。

## Consequences

- PRD §6.2 的关键形状 3（"任一 fetch 挂掉，简报照样出"）从口号变成类型：图节点拿到的是**结构化的缺失原因**，PRD 里提到的 `coverage_gaps` 有了具体形状。
- 三个 server 是三个独立进程，统一信封要求一个共享类型包，否则契约会散成三份。这会影响目录结构。
- **连带效果**：数据源故障被信封吸收成了正常返回。所以图层要做的失败隔离，只剩"工具链路本身坏了"（子进程死亡、超时、协议错误、代码 bug），不再需要处理"新闻源今天没更新"。两层职责因此不重叠 —— 这一条是下一层编排设计的前提。
