# LLM 录播按 (节点名, 输入数据哈希) 索引；查不到就报错；两层开关分开

LLM 层复用 ADR-0003 的形状：一个 `LLMClient` 协议，`live` 与 `replay` 两个实现。回放的 key 是 `(节点名, 关键输入字段的规范化哈希)` —— 哈希的是**输入数据**（`request_text` / `slots` / 冻结的 sections），**不是 prompt**。

两条硬规则：

1. **回放时查不到 key 直接报错，绝不 fallback 到真实调用。**
2. **数据层与 LLM 层用两个独立开关**：`MINING_DATA_MODE` 与 `MINING_LLM_MODE`，各自 `replay | live`，都默认 `replay`；`--live` 是把两个都置为 `live` 的语法糖。

## Considered Options

- **按 prompt 全文哈希**：语义最直白。否决 —— prompt 改任何一个字哈希就变、fixture 全废，而 prompt 恰恰是实现阶段一定会反复改的东西。
- **按 `(节点名, 第 N 次调用)` 序号**：prompt 随便改都不失效。否决 —— 顺序敏感：节点里多一次调用、或分支顺序变了，后面全部错位**且不报错**，`parse_intent` 会静默拿到 `narrate` 的响应，这种 bug 很难查。

## Consequences

- 哈希输入数据而非 prompt，把"调 prompt 措辞"与"换录播数据"解耦：改措辞不失效，换数据才重录 —— 而换数据本来就该重录。
- 查不到就报错这一条，把"prompt 大改后忘了重录"从悄悄变化的结果变成响亮的失败；也保证"离线确定性"不会被一次静默的网络调用破坏（否则测试是薛定谔的绿）。
- **两个开关分开的具体理由**：调一句导读的措辞不该被迫把 LME 切到真实抓取（要无头浏览器、要过 Cloudflare）。单个开关会让"改 prompt"这个高频动作拖上整条浏览器链路。
- 每个 LLM 节点因此需要**声明哪些字段喂给模型**，那些字段即 key 的组成部分 —— 这是节点的一个小契约。
